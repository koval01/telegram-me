# План перехода на Rust

Где воркер всё ещё тратит время в Python, каким путём оставшийся горячий путь
переходит в Rust и в каком порядке. Правило, которому всё это следует: тяжёлая
работа выполняется нативно; нативный код, который мы пишем сами, пишется на
Rust (готовые компоненты могут быть на C, C++ или Rust); Python — это клей:
бизнес-правила, связывание компонентов, оркестрация и скрипты, ничего на
горячем пути.

По дороге не меняются две вещи: ответы REST `/v1` и схема GraphQL (обе
зафиксированы в `tests/snapshots/`, REST — побайтово) и развёртывание (Docker,
compose, `deploy/remote-deploy.sh`, виртуальные машины с 1 ГБ памяти).

## Аудит { #audit }

Измерено с помощью [`scripts/audit.py`](https://github.com/koval01/telegram-me/blob/main/scripts/audit.py)
на Apple Silicon (8 ядер, Python 3.13), внутри процесса: t.me заменён
записанными страницами, кэшем служит кэш в процессе (L1
[двухуровневого кэша](caching.md)); память — на Linux (arm64,
Python 3.14). База для сравнения — `main` после двухуровневого кэша (PR #201).
«Выделено» — пик выделений памяти Python за время обработки одного запроса
(tracemalloc). Абсолютные значения стоит воспринимать как относительные.

```bash
uv run python scripts/audit.py --stages        # по эндпоинтам и по этапам
RAYON_NUM_THREADS=1 uv run python scripts/audit.py  # стоимость CPU на одном ядре
uv run python scripts/audit.py --memory 200    # RSS цикла запросов ленты (Linux)
```

### Память воркера { #memory-per-worker }

Linux, arm64, Python 3.14 (`scripts/memory_profile.py`, `scripts/audit.py --memory`):

| | RSS | Анонимная |
|---|---|---|
| Только интерпретатор | 9.0 МиБ | 3.4 МиБ |
| Главный процесс granian (супервизор) | 43.7 МиБ | 26.2 МиБ |
| Воркер с собранным приложением, без нагрузки | 85.3 МиБ | 63.2 МиБ |
| Воркер после 20 000 смешанных запросов к 1 200 каналам (учтено 41 МиБ в кэше процесса) | 187–212 МиБ, пик 220 МиБ | |
| Воркер, обслуживший 200 лент из 100 каналов | пик 220 МиБ | |

Собственные живые объекты Python держатся на уровне ~13 МиБ на протяжении
всей смешанной нагрузки (tracemalloc); остальное — интерпретатор с импортами,
кэш в процессе, нативные буферы и то, что malloc удерживает между всплесками.

Базовый объём воркера — интерпретатор и импортированное приложение (FastAPI,
pydantic, strawberry, redis-py, нативное расширение) плюс до
`MEMORY_CACHE_MAX_MB` под L1. `WEB_CONCURRENCY` воркеров дублируют всё это,
включая L1.

### Что из этого следует { #what-it-shows }

- Почти вся CPU-ёмкая работа помимо парсера и ранжирования приходилась на
  **сборку ленты**: 41 мс Python на ленту из 100 каналов с удержанием GIL,
  ~20 МиБ короткоживущих объектов Python и остановка всех остальных запросов
  воркера на это время. Это самая крупная отдельная статья.
- Следующая — **конвейер страницы после парсера** (0.5–2.6 мс pydantic с
  удержанием GIL на страницу, дважды при промахе `/v1/body`). Она важна для
  тактов обновления и холодного трафика, а не для попаданий в кэш.
- **Попадания в кэш уже дешёвые** (0.07–0.33 мс). Там остаётся нижняя граница
  на запрос — мост ASGI в granian и FastAPI — и pydantic для `/v1/post` и
  превью.
- **GraphQL** стоит ~0.85 мс Python на запрос независимо от данных.
- Части, ограниченные вводом-выводом (HTTP-клиент, Redis), уже нативные или
  на C; Python добавляет там накладные расходы на команду, а не ограничивает
  пропускную способность.
- **Ранжирование** (Rust) теперь самая крупная статья CPU в ленте: ~80 мс на
  2 000 постов на одном ядре. Его оптимизация не зависит от того, где
  работает клей.

## Варианты { #options }

### (a) Оставить оболочку granian/FastAPI, перенести целые конвейеры в нативный код { #a-keep-the-granianfastapi-shell-move-whole-pipelines-native }

Работа каждого эндпоинта становится одним нативным вызовом: загрузить,
разобрать, валидировать и отрендерить байты с отпущенным GIL; нативный кэш,
single-flight и ограничитель частоты. В Python остаются маршрутизация,
настройки, флаги функций, отображение ошибок, правила свежести ленты и
планирование обновлений.

- **За:** постепенность, каждый шаг выкатывается отдельно и проверяется
  побайтовыми снапшотами; OpenAPI (из моделей pydantic), GraphQL и CLI
  остаются как есть; бизнес-правила остаются в Python; Docker и скрипты
  развёртывания не меняются. Этим путём уже прошли парсер, ранжирование и
  кэш L1.
- **Против:** нижняя граница на запрос остаётся (мост ASGI в granian,
  FastAPI, ~50 мкс на запрос, ~20 тыс. запросов/с на воркер), как и полный
  интерпретатор на каждый воркер. GraphQL остаётся в Python.

### (b) HTTP-сервер на Rust (axum/hyper на tokio), обслуживающий `/v1` { #b-a-rust-http-server-axumhyper-on-tokio-serving-v1 }

Сервер на Rust; Python встроен (PyO3) или вызывается только для
бизнес-правил.

- **За:** самая низкая граница (десятки мкс и в несколько раз больше
  пропускная способность на ядро), один многопоточный процесс вместо процесса
  на воркер, а значит один кэш L1 и один пул HTTP на сервер вместо одного на
  воркер — самая большая экономия памяти.
- **Против:** одномоментная замена сервера, маршрутизатора, middleware,
  отображения ошибок и генерации OpenAPI; встроенный интерпретатор
  возвращает GIL для каждого правила, которое он выполняет, поэтому правила
  должны стать данными или кодом на Rust, чтобы был выигрыш; GraphQL
  потребует порта на Rust (async-graphql) с идентичной схемой и ошибками либо
  останется вторым сервисом на Python. Правила перестают быть «легко
  изменяемыми в Python».

### (c) Основной сервис на Rust и тонкая управляющая часть на Python { #c-a-rust-core-service-and-a-thin-python-control-plane }

Бинарник на Rust обслуживает `/v1` (а позже GraphQL) и запускает обновление
ленты; Python отвечает за конфигурацию, CLI, фикстуры и скрипты и, возможно,
за GraphQL отдельным процессом, который обращается к ядру.

- **За:** тот же выигрыш во время работы, что и (b), без встраивания; чёткая
  граница.
- **Против:** два процесса на виртуальную машину, которые нужно разворачивать,
  настраивать и отслеживать; управляющей части нужен интерфейс (файл
  конфигурации, административный API); та же одномоментная замена сервера,
  что и в (b), а всё, что сегодня является клеем на Python (флаги функций,
  правила свежести), придётся заново выразить на Rust или в конфигурации.

### Рекомендация: (a), поэтапно { #recommendation-a-staged }

Вариант (a) даёт выигрыш по CPU и GIL там, где он измерен (сборка ленты,
конвейер страницы, разрешение GraphQL), без рискованной замены. Каждый этап
переносит целый конвейер в `telegram-me-native`, выкатывается отдельно,
проверяется побайтовыми снапшотами и даёт свой измеренный выигрыш. Когда
конвейеры станут нативными, процесс уже будет ядром на Rust за оболочкой на
Python: в Python останутся нижняя граница ASGI/FastAPI в ~50 мкс и по
интерпретатору на воркер. Стоит ли заменять это фронтом на axum (движение в
сторону (c)), решается тогда, по цифрам (этап 6), а не сейчас.

## Этапы { #stages }

Каждый этап: снапшоты (`make snapshots`, побайтовые хэши) без изменений, свои
цифры до и после, свой PR.

1. **Нативная сборка ленты** — *сделано в этом выпуске.* `FeedService`
   передаёт байты страниц из кэша в `telegram_me_native.build_feed` и
   получает обратно байты ответа (один вызов, GIL отпущен): чтение страниц,
   сигналы ранжирования, ранжирование, рендер. В Python остаются правила
   stale-while-revalidate и популярность. См. [результаты](#stage-1-results).
2. **Нативный конвейер страницы.** Разбор, валидация и рендер одним вызовом:
   `parse_channel_page` сразу возвращает представление для кэша и
   отрендеренные байты `/v1/body` (и `/v1/more`) с теми проверками схемы,
   которые сегодня делает pydantic (нормализация URL — pydantic-core
   использует тот же крейт `url`, — допустимые значения literal, значения по
   умолчанию, валидаторы полей, отбрасывание постов, не прошедших
   валидацию). Модели pydantic остаются документированной схемой (OpenAPI,
   типы GraphQL) и становятся эталоном в дифференциальном тесте на фикстурах
   и сгенерированных постах. Убирает 0.5–2.6 мс Python с удержанием GIL на
   страницу и второй рендер при промахе `/v1/body`; такты обновления
   перестают требовать GIL.
3. **Нативное чтение из кэша.** `/v1/post`, `/v1/preview` и `/v1/previews`
   рендерятся нативно из байтов кэша (извлечь один пост, отрендерить превью),
   так что ни одно попадание в кэш не создаёт объектов Python. Опирается на
   рендерер этапа 2.
4. **Нативный уровень Redis и популярность.** Клиент Redis на Rust (redis-rs
   или fred на рантайме tokio) за существующим протоколом `Cache` и
   двухуровневым кэшем, плюс популярность и блокировка лидера; один сетевой
   круг на ленту для всех её страниц (`MGET`). Согласуется с работой по
   объединению запросов между воркерами, которая тоже живёт на Redis.
5. **Разрешение GraphQL.** Резолверы читают нативно отрендеренные байты, а
   самые тяжёлые выборки (`body.posts`) проецируются нативно; схема остаётся
   за strawberry, так что снапшот SDL не меняется. Убирает большую часть
   ~0.85 мс на запрос.
6. **Оболочка — по цифрам.** Когда этапы 1–5 сделаны, измерить, сколько
   стоят мост ASGI, FastAPI и middleware и сколько памяти занимает
   интерпретатор на воркер. Если это того стоит — обслуживать `/v1` фронтом на
   axum в том же образе (Python остаётся для GraphQL, документации и CLI) или
   запускать один воркер с нативными потоками вместо нескольких процессов.
   Ограничитель частоты и proof-of-work уже нативные (`ratelimit.rs`,
   `pow.rs`, PR #202).

Не планируется: сам алгоритм ранжирования. Его скорость — отдельная работа:
~80 мс на 2 000 постов на одном ядре — теперь самая крупная статья CPU в
ленте.
