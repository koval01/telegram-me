# Кэширование

## Что кэшируется { #what-is-cached }

| Ключ (префикс `tme:v2:`) | Значение | TTL |
|---|---|---|
| `json:body:page:{mode}:{channel}:{position}` | Готовый ответ `/v1/body` | TTL страницы (`CACHE_MODE`: 0 / 10 / 120 с) |
| `page:{mode}:{channel}:{position}` | Разобранная страница (сырой dict в виде JSON) | TTL страницы; для последней страницы при включённой ленте: `max(page TTL, FEED_STALE_TTL)` |
| `more:{mode}:{channel}:{direction}:{position}` | Готовый ответ `/v1/more` | TTL страницы |
| `preview:{channel}` | Разобранное превью или `null` для неизвестных каналов | `PREVIEW_CACHE_TTL` (1 ч), 60 с для неизвестных |
| `feed:popularity` | Отсортированное множество канал → оценка | — (затухание обеспечивает рефрешер) |
| `feed:refresher-leader` | Токен рефрешера-лидера | 30 с, продлевается каждые 5 с |

`{mode}` — это режим парсера, поэтому экземпляры с `full` и `simplified` могут
делить один Redis, не смешивая результаты. Имена каналов приводятся к нижнему
регистру.

Каждое значение хранится вместе со временем записи
(`"<unix time>\n<payload>"`), что позволяет вызывающему коду применять
собственные правила свежести поверх срока жизни в бэкенде — именно так
работает stale-while-revalidate в ленте.

## Бэкенды { #backends }

**Redis / Valkey** (задан `REDIS_URL`): общий для всех воркеров и серверов.
Команды прерываются по тайм-ауту через `REDIS_TIMEOUT` (0.5 с). Первая же
ошибка размыкает circuit breaker: Redis обходится стороной 30 секунд, и
запросы обслуживаются без кэша, так что сбой Redis стоит не больше одного
медленного запроса на воркер, а не по одному на каждый запрос. Ответы
разбирает hiredis (C).

Запрос ленты или превью выполняет до 100 обращений к кэшу одновременно,
поэтому при пуле соединений (`2 × TELEGRAM_MAX_CONCURRENCY` на воркер, не
меньше 32) всплеск ждёт свободного соединения до `REDIS_TIMEOUT`. Команда, не
получившая соединения, считается промахом; исчерпание пула — локальное
ограничение, поэтому circuit breaker не размыкается.

**Память** (по умолчанию): LRU-словарь в каждом воркере со сроком жизни у
каждой записи, ограниченный `MEMORY_CACHE_MAX_MB` реальной памяти: значения
хранятся сжатыми (zstd уровня 1; zlib на Python 3.13), а лимит учитывает
сжатое значение, ключ и служебные данные каждой записи. Отрендеренная страница
занимает там 14–53 КиБ вместо 93–700 КиБ в виде Python `str` (см.
[Производительность](performance.md#memory)).

В обоих бэкендах значения — байты UTF-8. Хранение JSON как `str` стоило до
четырёх байт на символ (одно-единственное эмодзи расширяет всю строку) и
кодирования при каждом попадании в кэш.

## Заранее отрендеренные ответы { #pre-rendered-responses }

Для `/v1/body` и `/v1/more` в кэше лежит итоговый JSON. Загруженная страница
один раз разбирается, проверяется и сериализуется; каждое попадание в кэш
отдаётся как байты. Это делает попадания в кэш примерно в 5 раз дешевле, чем
повторная валидация разобранной страницы на каждый запрос (см.
[Производительность](performance.md)).

## Объединение запросов { #request-coalescing }

`SingleFlight` ключует выполняемую работу по ключу кэша. Пока у t.me
запрашивается страница, все остальные запросы той же страницы ждут эту одну
задачу вместо того, чтобы отправлять свои, — всплеск из 1000 запросов к
некэшированному каналу порождает один запрос к источнику. Отключившийся клиент
не отменяет общую задачу.

## Защита источника { #upstream-protection }

- Семафор на процесс ограничивает число одновременных запросов к t.me
  (`TELEGRAM_MAX_CONCURRENCY`, 32).
- Неизвестные каналы кэшируются как `null` на 60 с.
- Кэширование на edge Cloudflare включается через `Cache-Control` (см.
  [Обратный прокси](../deployment/reverse-proxy.md#cloudflare)).
